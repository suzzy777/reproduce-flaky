MSR 2026 Paper #240 Reviews and Comments
===========================================================================
Paper #240 A Reproducible Dataset of Flaky-Test Failures


Review #240A
===========================================================================

Overall merit
-------------
1. Reject

Paper summary
-------------
This paper introduces a new dataset (ReproFlake) for reproducing flaky test failures. Created by mining Jira issues and the iDoFT dataset of flaky tests, the newly introduced dataset includes the source code version of flaky tests in Maven projects and different code patches to (1) reliably reproduce the flaky failure at execution, (2) repair the flaky test, (3) verify that the applied repair patch is effective. It also comes with specific information to reproduce other types of flaky tests (e.g., the random seed for OD flaky tests) and Dockerized environment to ensure the full reproducibility of the flaky tests. The overall goal of this dataset is to facilitate future research regarding root cause localization and repair of flaky tests.

Strengths and Weaknesses
------------------------
Strengths

- The dataset targets a well-known and timely challenge of flaky tests.
- The paper proposes a set of strategies tailored to different categories of flaky tests, thoughtfully addressing their diverse underlying causes.

Weaknesses

- The paper is difficult to read and follow in its current form.
- Several analyses would benefit from greater rigor.
- The rationale behind some methodological choices is not sufficiently explained.

Comments for authors
--------------------
## Soundness

Addresing flaky tests is a timely software engineering challenge with many papers published recently. The authors’ efforts are commendable, as they address the important gap of reliably reproducing inherently intermittent flaky test failures and validating that proposed fixes are effective in real project environments. The authors leveraged a variety of tools (iDFlakies, NonDex, FlakeSync, and 100 repeat runs) to identify flaky test failures, ensuring they cover a diverse set of problems. 

However, the dataset creation process lacks clarity in various parts and is difficult to follow. The text at L470-L474 uses multiple overlapping terms (workflow, process, guideline, methodology), making it unclear whether these refer to the same concept or different ones. In addition, the goal of manual inspection (L600) remains unclear until the reader figures it out at some point. This might need to be clearly stated. The manual inspection methodology lacks information on how the "fixed merged commit and preceding commit" are located. 

Other points:
- L803: “Assigned 15 labels” unclear how these labels were defined.
- L807: Not specified which "GPT" model is being used.
- L808-L809: The definition and distinction between “subcategories” and “higher-level categories” is not clarified. The methodology used to group "subcategories" into high-level categories should be explicitly described.

## Relevance 

The focus on the reproducibility of flaky test failures and their repair fixes in containerized project environment, which aligns closely with pressing challenges faced by both researchers and practitioners addressing flaky tests. The covered problematic is highly relevant.

## Novelty

The introduced dataset is an innovative extension of the state-of-the-art iDoFT dataset, using Jira Issues information and source code versions to enable the reproducibility of flaky test failures. 

## Presentation

Overall, the paper suffers from a lack of clarity and consistency, which makes it hard to follow. Few points are described below, but it would greatly benefit from careful rephrasing to improve clarity and flow.

- L167: The size and content of the dataset should be described more straightforwardly.
- L204: “Should not be guaranteed” => “is not guaranteed.”
- L277: Suggest clearer phrasing: “that fails upon rerun is detected.”
- L280: Prefer “we use Docker” unless emphasizing an exceptional use.
- L280–L282: Rephrase “We can…” for greater clarity if the goal is to express what is possible with Docker images. As example: “Docker allows specifying the OS, source code, and other components. The resulting image can be easily reused for reproducible execution across environments.”
- L345: Check consistency regarding the "one second" vs. 2s (see L344).
- L470–L474: As already mentioned, too many overlapping terms are used (workflow, process, guideline, methodology). Choose a consistent vocabulary and clarify the relationship between terms. Move Figure 3 closer to its explanation.
- L605: “There were issues where there were…” => needs rephrasing.
- L615: A clearer, more straightforward way to present the conflict matrix is needed. The provided description does not help easily read Table 1.
- L818: When reporting that “dependency resolution error accounts for 86.3%,” clearly state which categories are included, using the exact labels shown in the corresponding figure.
- L1027: “In some cases, the result may not be available” Please specify which result this refers to.
- L608: Correct the “, ,” typo.
- L88: Missing final period.

## Reproducibility

The process used to create the dataset is presented, but includes several unclear parts that might hinder reproducibility. However, the dataset itself is made openly available on Zenodo.

Questions for authors' response
-------------------------------
1. What is the difference between workflow, process, guideline, and methodology when describing the dataset creation process?
2. What nuance is made between guideline step (L471 and L616) and section (L475)?



Review #240B
===========================================================================

Overall merit
-------------
1. Reject

Paper summary
-------------
The study constructs a dataset of 1,115 reproducible flaky tests, packaged in Docker images containing the code and all necessary dependencies. The dataset is built from two sources: 63 flaky tests identified through an analysis of project issue reports in Jira and 1,052 tests taken from the existing iDoFT dataset after verifying their reproducibility. The flaky tests extracted from Jira are further classified, such as time-dependent and order-dependent, using existing tools. The study also examines the challenges of reproducing flaky tests, the error types observed in test failures, and the lines of code changed and their locations during fixes, finding that dependency resolution is the most difficult challenge, assertion errors are the most common error types, fixes involve more test code than production code, and lines of code changes vary across flaky test categories.

Strengths and Weaknesses
------------------------
Strengths
- A reproducible dataset of flaky tests

Weaknesses
- Several inconsistencies in data presentation make the paper difficult to follow
- The study lacks novelty
- There are some concerns with the methods used to curate and analyze the dataset
- Threats associated with curating and analyzing the dataset are not reported

Comments for authors
--------------------
Novelty

- The study lacks novelty and is primarily focused on curating a reproducible dataset of flaky tests. The research questions mainly aim to describe the experience of curating the dataset and the dataset itself, which contains only 63 new flaky tests. Several of the findings are already well-known. For example, challenges associated with running old commits and common suggestions for fixing flaky tests have been widely reported.

Soundness

- For the manual inspection (Section 4.2.1), selecting issues from a broader range of projects rather than relying solely on random sampling could have improved the generalizability of the findings. The number of projects represented in the selected 300 issues is not specified, nor is it clear how many projects contain flaky tests. Additionally, 3% of 10,808 is not 300.

- The rationale for using open coding is not provided. If the goal is to determine whether a test is flaky and to identify pre-defined types, then open coding may not be appropriate. Most of the specified tasks, such as checking whether the project compiles and reproducing flaky tests, are procedural and do not require open coding. While it is commendable that two authors independently performed these tasks for each issue, open coding was not necessary for them.

- It is unclear how many flaky tests are used to investigate RQ1. Section 5.1 presents different numbers of tests and modules without clearly specifying which data is used for this research question. The results for RQ1.1 also do not provide concrete numbers for the various challenges encountered in reproducing flaky tests. For example, how many tests could not be reproduced due to compilation errors? Without such numbers, reporting the relative percentage of dependency resolution errors is not meaningful.

- In RQ1.1, the process of assigning labels to log files and using them to create regex rules for categorizing compilation errors is unclear. For example, what do these labels represent? Are they error types? How are the labels used to construct the regex rules? Additionally, how were the examples selected for GPT?  

- In RQ1.2, the rationale for introducing time-related changes in the fixed TD tests to assess whether they still exhibit flaky behavior is unclear. Such modifications could themselves introduce flakiness rather than reflecting the developers’ original changes. Additionally, if 117 out of 805 fixed ID tests still exhibit flaky behavior, it is unclear why they were included in the dataset.

- Code changes involve both additions and deletions of lines, so it is unclear why the changes reported in RQ2.2 are measured as additions minus deletions. It collapses two meaningful quantities into a single net value. This can obscure the actual size or nature of the modifications.

Relevance

- A reproducible dataset of flaky tests can be valuable for advancing research in this area, and the authors have clearly invested substantial effort in curating the ReproFlake dataset. However, the study contributes only 63 new flaky tests. When these are further divided by flaky type, the numbers per category become even smaller, making it difficult to determine whether any meaningful patterns can be reliably inferred. 

Presentation

- The use of Section and node terms used to represent data collection tasks is really confusing. Using the task names instead would be more expressive. Additionally, the sections are not included in the figure, which makes it more difficult to understand the process.

- Table 1 and its description in Section 4.2.1 are confusing. For example, the meanings of “0” and “X” are not explained. It is also unclear how to interpret the values in row six, which shows 3 under “compilable” and 7 under “flaky types.”

- In RQ2.1, four different types of flaky tests are reported from iDoFT, yet Table 3 lists only three types.

- an -> and (line 93), An extra “,” (line 608)

Replicability

- The artifact page includes the dataset, analysis results, and scripts used in the study. However, I was unable to extract the dataset (data folder) despite multiple attempts, as it consistently produced errors.

Artifact Assessment
-------------------
2. The artifacts are present but **not** sufficiently in line with what is
   declared in the submission form and in the paper

Questions for authors' response
-------------------------------
1. What specific knowledge gap does the study address? Given that it contributes only 63 new flaky tests, is this number sufficient to reveal meaningful patterns across flaky test types?

2. What is the rationale for using open coding when many of the tasks, such as checking compilability and reproducing tests, appear procedural?

3. In RQ2.2, why are code changes reported as additions minus deletions rather than additions plus deletions?



Review #240C
===========================================================================

Overall merit
-------------
1. Reject

Paper summary
-------------
This paper proposes a set of tooling, approaches, and a novel combination of data to create a "reproducible dataset of flaky tests" combining information from widely used, open datasets about flaky tests, and developer issues reporting problems with flaky tests from open source projects (specifically Jira issues in the Apache software ecosystem).

Strengths and Weaknesses
------------------------
__Strengths__
* Concept to extend current approaches to flaky test data to include real-work information about developer reported issues is interesting.
* Demonstrated broad examination of previous research and current gaps in existing flaky tests datasets

__Weaknesses__
* The proposed "reproducible" workflows had dependency errors accounting for an overwhelmingly representation of the mined sample set. These appear to be errors  introduced by experiment and tooling design, and were not necessarily inherent in the underlying data.
* Presentation the problem, the approach, the methodology, and the overall structure of the paper is challenging to follow. 
* There are sections that are repetitive, or were extensive qualitative phrasing is used to discuss a concept multiple ways. This would be much stronger with less words.

Comments for authors
--------------------
__Soundness__ 
* [-] Overall statistics for what was mined, tested, categorized, and included in the final dataset did not seem to match the proposed novel contributions as listed in the intro or outcomes.
  * Need to redo all tables, statistics, and metadata statistics from Section 4.3 to make clear what exactly is included in the dataset, what is not reproducible or consistent across all categories, and what is novel.
* [-] Section 3 "Example Flaky Test" did not substantially contribute to the methodology description or overall paper presentation. Recommend removing.
* [-] Figures 4 - 6 need "N = " per pie chart to demonstrate comparative sample set

__Relevance__
* [+] Connecting developer reports with widely-used datasets provides an additional level of information to examine and answer relevant research questions.
* [-] It doesn't seem like this specific approach or resulting dataset quite completed the connection towards a next-gen dataset based on this concept.

__Novelty__
* [neutral] This is not my specific domain of research, so I cannot comment on the overall novelty of these contributions.

__Presentation__
* [-] Overall, needs extensive editing to remove connective and qualitative language. 
* [-] Repetitive language across multiple sections. 
* [-]The sections appear to be disjoint, and do not have a singular collective voice or presentation.
* [-] Recommend restructuring the following sections entirely, and with the following order: 
  * Introduction - lines 39 - 71, lines 108 - 143
    * Recommend summarizing 72 - 96 into a single diagram with simplified steps as the intro
  * Background - lines 182 - 210
  * Methodology - move lines 210-660 into a separate section with subsections describing the tooling and decisions at each method step
* [-, minor] Figures and diagrams should be made accessible for black and white viewing/printing.
* [-] Sections 4.1 - 4.2 should be presented as a tables and flow diagrams to illustrate better the comparison between the fields in the dataset and the collection/workflow/systems per flaky test category
  * lines 465-496 need to be on the same page as Figure 3 for readers to reference

__Replicability__
* [+] Paper includes a public listing for the project, but this reviewer did not visit the site.
